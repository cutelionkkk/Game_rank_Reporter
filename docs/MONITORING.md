# 本地网页与选择性监测

## 启动

需要 Python 3.10+（推荐 3.12）、Node.js 22+（Google Play 使用）。在项目目录安装：

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
npm ci
python run.py --serve --open-browser
```

Windows 激活环境使用 `.venv\Scripts\activate`。macOS 安装后可双击根目录的 `启动游戏雷达.command`。

网页地址为 `http://127.0.0.1:8765`；端口可通过 `--port 8766` 更换。服务只监听本机。网页只管理监测范围，不显示或修改通知渠道密钥。网页“立即监测”采集并导出数据，不发送通知。关掉进程后网页停止；历史与选择保留在本地。

## 选择榜单版块

1. 打开“榜单版块”，勾选商店、国家、榜单类型和游戏品类。
2. 点“添加所选组合”。多个维度按组合生成版块，例如两商店 × 两国家 × 一榜单 × 两品类 = 八个版块。重复组合自动跳过，最多 100 个。
3. 设置爬升阈值、对比窗口和 Top N，点“保存设置”。可以单独停用某版块，或关闭整个榜单监测。
4. 点“立即监测”。尚未保存的修改会先保存；运行期间不能保存新配置。

支持免费榜、付费榜、畅销榜；可选范围不保证来源在每个国家/品类下都可用。失败会显示具体来源，不会用其他榜单冒充。Apple 的 7009 分类是 **Family（家庭）**，Google Play 对应旧配置 `casual` 的分类是 **Casual（休闲）**，网页明确标示两平台差异。

爬升计算为 **旧排名 − 当前排名 ≥ 阈值**。只比较同一商店、国家、榜单、品类且两次都在榜的游戏，不假设未在榜的游戏排名为 101。新上榜另列，不等于新发布。

- `comparison_hours=0`：与上次成功采集比较，展示实际间隔。
- `24 / 72 / 168`：找最接近窗口起点的成功快照，容许窗口起点后 1 小时的调度误差；实际间隔超过窗口两倍时不判定快速爬升。
- 默认窗口 24 小时，首次运行无排名信号，需要积累约一天的历史。
- 两次榜单深度不同时，新增/跌出仅在双方共有深度内判断；空响应和请求失败不写入排名快照。
- `consecutive_rise_days` 为兼容旧配置保留的字段名，实际含义是**连续上涨的采集次数**，不是天数，且必须延续到本次快照。

## 关注游戏公司

1. 打开“关注公司”，选择商店、国家，输入公司名或旗下游戏名搜索。
2. 通过开发者 ID、代表产品及商店账号链接确认候选账号，点“关注”。搜索可能返回相关游戏的其他发行商，不会自动按名称认定归属。
3. 编辑关注名称和地区代码，例如 `us, jp, kr`。同一账号可选 1–10 个国家，最多 50 个账号。同一公司有多个发行主体时分别添加，关注名称可以相同。
4. 若搜索找不到，可手动填写开发者 ID：iOS 使用开发者页面 `/developer/.../id123456` 中的数字；Google Play 使用开发者页面的 `id` 参数（不是游戏包名）。
5. 保存并运行。首次成功取得某账号/地区的目录只建立基线，不报警。

后续新增游戏分两类：

| 标签 | 条件 |
|---|---|
| 近期发布 | 首次发现，且商店原始发布日期距本次采集 0–N 天，默认 30 天 |
| 首次发现 | 首次进入已建立基线的目录，但发布日期较旧、未知或为未来日期；不认定为新发布 |

- 公司目录独立于排行榜，未上榜的公开产品也能被发现。
- 同一开发者账号、商店、游戏只产生一次新增事件；跨国家重复出现不重复产生新游事件。新增国家先建独立基线。
- 单轮报告按该轮事件展示；手动重复发送同一轮报告仍可能收到相同消息。没有对通知投递本身做 exactly-once 保证。
- 暂停后保留历史。恢复时未见过的产品仍按实际首发日期分类。
- App Store Lookup 每次最多返回约 200 款软件，Google Play 本工具最多读取 200 款产品；达到上限会标记目录可能不完整，不承诺全量。Google Play 新产品详情并发最多四个请求，已知产品复用缓存。
- 只能观察所选地区商店公开可见的产品；无法保证发现未公开、仅限测试、已下架、其他发行账号或未选地区的项目。
- 商店首发日期不是特定国家首次上线日期，也不采用最后更新日期冒充首发日期。已知 Google Play 产品的详情缓存不会每轮刷新。

## 每日运行和通知

```bash
python run.py --dry-run          # 采集两个已启用模块、报告、导出，不通知
python run.py --crawl            # 仅采集两个已启用模块
python run.py --report           # 最近一轮报告（含失败状态）
python run.py --export-analysis  # 导出最近一轮数据
python run.py                    # 原有完整流程，含已配置的通知渠道
python run.py --setup            # 原有通知配置向导
```

网页不内置定时调度。已有每日任务继续调用 `run.py` 即可，新配置自动生效。没有既有任务时，可自行使用 cron/系统计划任务；示例为每天 09:00（电脑需运行且能联网）：

```cron
0 9 * * * cd /absolute/path/Game_rank_Reporter && /absolute/path/Game_rank_Reporter/.venv/bin/python run.py >> monitor.log 2>&1
```

本地网页和命令行共用进程锁，避免同时抓取产生重复快照。本轮失败不会回退到旧成功数据冒充本轮结果。部分来源失败仍生成可用部分的报告，命令返回非零状态提醒排查。开发验证不发送通知、不安装系统定时任务。

## 升级与数据

- 保留原 `settings.json` 即可；旧版 `platforms × charts` 或缺少国家的 `chart_list` 自动兼容。显式 `chart_list: []` 表示不选榜单，不会回退默认榜单。
- SQLite 旧表没有国家字段。首次升级前自动保存 `rankings.db.pre-country.bak`，再事务迁移；旧记录归入原设置的 `country`（未配置则为 `us`）。若历史上切换过国家，旧数据无法自动还原，请先备份并人工分离，或从空数据库积累。
- 保存网页设置会保留原通知配置。配置文件通过原子替换写入；网页没有发送通知接口。
- JSON 输出升级为 schema 2：`charts` 的键是 `商店_国家_榜单[:品类]`，例如 `ios_jp_free:puzzle`。`current`、`changes`、`previous_time`、实际间隔、来源状态和阈值都位于该版块内。`companies` 包含账号、地区目录状态和本轮事件。旧版固定 `ios_free` / `gp_free` 消费方需调整。
- 网页导出与 CLI 导出使用同一分析；`analysis_data.json` 是 CLI/监测作业保存的结果。无网络也可以查看已保存历史并生成报告。

## 验证

```bash
python -m unittest discover -s tests -v
node --check gp_scraper.js
node --check web/app.js
```

测试使用临时数据库和模拟来源，覆盖旧表迁移、地区隔离、时间窗口、阈值一致性、基线/去重、失败保留状态、网页配置与密钥隔离。实际商店接口受地域、访问频率及页面变化影响，失败请以“采集状态”中的信息为准。
